Probing Recurrent Reasoning: Inside Huginn’s Hidden States

Shane JanneySeptember 2026
Read the paper ↗Explore the results ↓

I wanted to see whether I could learn more about a model’s answer by inspecting its internal states than by asking it for an explanation. I used Huginn for this because it lets me change how many times it runs its recurrent block before producing a token. I could compare runs with different amounts of computation while keeping the model itself fixed.

I gave it a set of rule-following problems and trained small classifiers to identify which rule applied. Those classifiers did much better with the later internal states than with the written explanations. But Huginn’s own answers were still around chance. I also tried swapping states between problems, and didn’t find a clear effect on its answers. Here’s the setup, the results, and why I’m being careful about how I interpret them.

What are we looking at, exactly?

A language model takes text and predicts what should come next. It breaks the text into tokens, which can be words, parts of words, or punctuation, and represents them as lists of numbers. A neural network transforms those numbers through a series of calculations. At the end, the model assigns scores to possible next tokens.

Two kinds of numbers matter here. The weights are the parameters learned during training. They determine how the network processes its input. The activations are the values produced as a particular input passes through it. Different prompts produce different activations even when the weights stay fixed.

Those activations are what I inspect in this project. They aren’t sentences we can just read, and individual numbers don’t usually come with a neat meaning. I need a test that asks whether they contain information about something specific.

Why an explanation isn’t enough

Asking a model to explain its answer gives us another piece of generated text. That explanation might be useful, but we can’t assume it lists the factors that caused the answer. To check that, I compare three things: what the model says, what a classifier can extract from its internal states, and what happens when I intervene on those states.

This is part of mechanistic interpretability: trying to understand a model by examining and testing its internal computation. My experiment addresses a small part of that problem. I’m tracking one known label in a controlled task, not trying to translate the model’s entire internal state into English.

How a recurrent network works

A recurrent network feeds an updated state back into the same computation. The state changes with each pass, while the weights remain fixed. You can think of the state as the numbers the network carries forward from the previous pass.

Why I used Huginn

Huginn lets me change the number of passes through that shared core while leaving its weights alone. That differs from a traditional sequence RNN, which often updates its state as it reads successive tokens. Here I’m changing the number of internal passes before the next token is produced.

Huginn feeds a hidden state through a transformer core, then feeds the result back through the same core. Each pass updates the state without changing the weights. For this experiment I used 4, 8, 16, and 32 passes, and saved the states along the way.

If you’re reading the equation below, e is the prompt representation, h is the internal state, and G is the core doing the update. θ is the set of model weights. After the last pass, a decoder turns the state into scores for the next token.

hk = Gθ(hk−1, e)

To read these states, I trained a probe: a small classifier that takes an activation vector and predicts a label. That’s worth spelling out because the probe and Huginn aren’t doing the same job. My classifier might find information that helps it predict the label even if Huginn ignores that information when answering.

I used activation patching to check whether changing a state would affect the answer. In practice, that meant saving a state from one problem, inserting it into another run, and letting the model continue.

So there are two separate questions throughout this page. Can the probe identify the right rule? And does that information affect Huginn’s answer? A good result on the first question doesn’t settle the second.

Building the task

I generated 500 policy problems, grouped into 250 pairs. Each has a base rule and an exception. The base rule gives an allow-or-deny decision. To find out whether the exception applies, the model has to follow a chain of relationships and check a property at the end. If it applies, the answer reverses.

I know which rule should determine each answer because I generated the problems. That gives me the label for the probes: base rule or exception. I also made sure each label appears equally often with “allow” and “deny.” Otherwise, a classifier could get credit for recognizing the answer without telling me anything about which rule applied.

I used 350 examples for training, 76 for validation, and kept 74 for testing. For each run, I saved the answer scores and generated explanation, plus the last prompt token’s state after every loop. The runs use the same seed for a given example: the first four loops of its 32-loop run match its four-loop run.

The split keeps the final evaluation separate from the examples used to fit or tune the classifiers. The validation set helps choose a configuration; the test set checks how that choice performs on held-out problems. With only 74 test examples, a few different predictions can noticeably change the score.

Here’s what I ran on those saved outputs:

  1. Internal-state probes. Regularized logistic classifiers predict the path label from hidden states. I also probe the pre-recurrence representation and randomly initialized loop-0 state as baselines.
  2. Text monitors. TF–IDF features and a frozen MiniLM encoder provide two ways to read the generated rationale. Every line containing FINAL: is removed before monitoring.
  3. Activation patching. A recipient receives an internal state from a paired counterfactual donor. I then measure the change in its answer scores and whether its choice flips toward the donor.
A few terms used in the tests

Logistic classifier: a small model that combines its input values with learned weights to predict one of two labels. Regularization: a constraint that discourages large weights and helps limit overfitting to the training examples.

TF–IDF: represents text using how often words appear, with less emphasis on words common across documents. MiniLM: a pretrained text encoder that converts an explanation into a numerical representation. “Frozen” means I don’t change that encoder’s weights; I fit a classifier on its outputs.

Rationale: the explanation I ask Huginn to generate. Counterfactual pair: two related problems where a controlled change alters which rule or answer applies.

There is training involved here, but it’s only for the small monitoring classifiers, not Huginn. I choose the probe’s regularization setting using the validation set, refit that configuration on the training and validation examples together, and evaluate it on the held-out test set.

The probe results

The first thing I checked was whether I could already recover the label before the recurrent core did any work. The probe on the prompt’s prelude representation scored 50.0% balanced accuracy; the probe on the initialized state scored 47.3%. Neither result distinguishes itself from chance.

In the 32-loop run, the scores start climbing around loops 9–12. At loop 16 the probe gets 91.9% balanced accuracy, and the highest score is 94.6% at loop 18. It finishes at 86.5%. I’ve plotted all the loops below, including the uncertainty intervals, so you can see the variation rather than just the best score.

Balanced accuracy gives the two labels equal weight. A classifier that always picks the same label scores 50%, our chance reference. The shaded band shows a 95% bootstrap interval: I repeatedly resample the test examples and recalculate the score to estimate how sensitive it is to the sample. It doesn’t account for every source of uncertainty, such as changing the dataset or model.

How to read balanced accuracy

Balanced accuracy averages recall for the two labels: BA = ½(recallbase + recallexception). A constant classifier scores 50%. Here it measures how well an external probe identifies the decision path—not how often Huginn answers the policy question correctly.

Checking the written explanations

The classifiers trained on the explanations didn’t do nearly as well. At 16 and 32 passes, both trail the internal-state probe. Their 95% intervals include chance at all four depths.

I put Huginn’s own task accuracy underneath the monitor scores because it’s easy to confuse the two. The probe identifying the correct rule 91.9% of the time doesn’t mean Huginn answered 91.9% of the problems correctly. At 16 passes, its task accuracy was 50.0%.

The bars compare monitors on the same examples within each depth. At shallow depths, some runs don’t produce a usable nonempty explanation, so fewer examples qualify for that comparison. The task-accuracy number still uses all 74 test examples.

These results don’t tell me that useful reasoning is happening somewhere the explanation can’t reach. They tell me what these particular classifiers can recover. Another text monitor might do better, and information in an internal state might help my probe without helping Huginn. I don’t have a verified record of the model’s reasoning to compare against.

Swapping states between problems

For the patching test, I take the internal state from one problem and insert it into its paired counterfactual’s run. The first problem is the “donor”; the run receiving the state is the “recipient.” I replace the last prompt token’s state at a chosen loop, let the model continue, and check whether its answer moves toward the donor’s answer.

I also run controls: replacing a state with itself, taking a state from an unrelated problem, and using a donor with the same answer. Those comparisons help check whether a change is specific to the counterfactual, rather than just a consequence of disturbing the state.

An answer flip means the preferred answer changes toward the donor’s answer. The logit margin is the difference between the model’s raw scores for the answer options. It can move a little without changing which answer wins, so I check both.

None of the 24 pairs produced a donor-directed answer flip at any tested loop. There were small changes in answer margins, but they didn’t clearly separate from the unrelated-donor control. I wouldn’t treat this as proof that the state has no effect: 24 pairs is a small sample, I’m only patching one token position, and the model wasn’t reliably solving these problems in the first place.

What I still need to check

I found a label that becomes easier to read from Huginn’s later states, but I haven’t shown that it uses that label to answer. The paper calls this late linear decodability without demonstrated behavioral use. The “demonstrated” part matters: the patching test is too limited to rule out an effect.

I’d start the next round with a task Huginn can solve reliably. Right now, a failed patch is difficult to interpret when the original answer is often wrong. I also need to repeat the runs with different seeds and datasets, check more carefully for shortcuts based on the words in the prompt, and recompute the intervals by resampling whole pairs.

The patches could be more precise too. I replaced an entire token state, which changes a lot of features at once. Testing a smaller, targeted change would help narrow down what is responsible for any effect.
