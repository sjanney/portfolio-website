Learned Indexes for Filesystem Metadata: A From Scratch Implementation and Benchmark Study

July 23, 2026

I kept seeing learned indexes described with a claim that sounded almost too clean: an index is just a function from a key to a position, so why store a tree if a tiny model can learn that function instead? The papers made the idea look elegant. I wanted to know what it felt like when you actually had to implement the thing.

Filesystem metadata seemed like a good place to push on it. A metadata lookup is basically a key value problem wearing a filesystem costume. Given a filename, path, or inode number, find the record that tells you where the data lives. Traditional filesystems solve that with trees and related structures, which is completely reasonable, but millions of small files make the memory and cache cost of all that pointer chasing hard to ignore.

So I stopped reading about learned indexes and built one in C. I also built the boring baselines myself, then pushed all of them through datasets as large as 5 million keys. The learned index hit 123.2 nanoseconds per lookup at 5 million uniform keys, roughly 3.4 times faster than my sorted array and 4 times faster than my simplified B+tree. Its index structure also used about 688 times less memory than that tree baseline.

Those numbers are real for this benchmark, but they are not a filesystem result. There is no disk I/O here, no page cache, no crash recovery, and no concurrency. I am isolating the index layer because I wanted to know whether the core idea survives before adding the rest of the system around it.

The part of tree indexes I wanted to challenge

B trees are not broken. That is important. They are one of the most successful data structures in systems because they behave well under updates and give predictable lookup costs. The thing I wanted to challenge was the amount of structure they have to keep around in order to do that. Pointers, node boundaries, and headers consume memory even though they mostly describe where the keys are rather than the keys themselves.

At small scales this is not very interesting. At millions of keys, it becomes a cache problem. A lookup can bounce through enough memory that the bookkeeping around the data starts to matter almost as much as the comparison count.

A learned index takes a different bet. Sort the keys, imagine their position as a function of the key value, and fit a model that predicts approximately where a key should live. The prediction is allowed to be wrong. During training I record the maximum error for each model, then do a bounded binary search around the predicted position. The model gets me close. The search makes the answer exact.

The annoying problem is insertion

The static case is the easy demo. A trained model describes one sorted dataset. Insert a key in the middle and every later position can shift, which means the error guarantees you measured during training are no longer automatically trustworthy. Trees handle that kind of update naturally. Learned indexes need an extra idea.

I used a small delta buffer inspired by ALEX. New keys land there immediately. A lookup checks the learned base index first and falls back to the buffer when needed. Once the buffer fills, I merge it into the sorted base array and retrain the model. It works, but it also hides a cost that becomes important later: most inserts are cheap until one of them pays for a retrain.

What I built so the comparison would be fair enough

I did not want to compare a hand tuned learned index against library code I barely understood. So all three structures are intentionally mine, with all the imperfections that implies.

The baseline is a sorted array with binary search. Lookups are simple and surprisingly competitive because the memory layout is so cache friendly. Inserts are terrible once the array grows because every key after the insertion point has to move.

The tree baseline is a simplified two level B+tree style index. Keys live in sorted leaf blocks of 128 entries, while a sparse root array points each lookup toward the right leaf. It is not a production B+tree and I do not pretend it is. It captures the local shifting and leaf splitting behavior I wanted to compare, but my implementation choices matter to the benchmark.

The learned structure is a two stage Recursive Model Index with the delta buffer. Stage 0 is a single linear model that chooses a Stage 1 model. Each Stage 1 model owns a slice of the key space and predicts a position plus an error bound. A lookup becomes a couple of arithmetic operations followed by a small exact search around that estimate.

I wrote the regression fitting, bounds, and search logic directly in C with the standard math library. That was partly for the experiment and partly because I wanted to understand where the abstraction leaked. It leaked most around updates.

How I tried not to give the model an easy benchmark

I tested sequential keys, uniform random keys, and lognormal keys. Sequential data is almost the dream case for a learned model. Uniform random data is much less obviously structured. Lognormal keys create the kind of clustering you might see around timestamps or size ranges. One funny detail: the lognormal generator clustered so aggressively that I only got about 2.86 million distinct values while aiming for 5 million. The benchmark reminded me that synthetic data has behavior of its own.

For lookups, I populated each index and ran 200,000 random point queries at dataset sizes up to 5 million keys. For inserts, I built the indexes from 80% of a dataset and streamed the remaining 20% in randomized order. I capped that test at 200,000 keys because the sorted array eventually spends so much time shifting memory that continuing mostly measures patience.

Everything ran single threaded in the same Linux container. The absolute latency numbers belong to that environment. The useful part is the relative behavior of the three implementations under the same conditions.

What happened

The learned index pulls away as the dataset grows

Uniform keys are shown here. Sequential and lognormal data followed similar broad patterns.

At 10,000 keys, the learned index is already more than twice as fast as the plain array. At 5 million keys it reaches 123.2 nanoseconds per lookup, about 3.4 times faster than the array and 4 times faster than my B+tree. The reason is not mysterious. Once trained, the RMI mostly does arithmetic and then searches a small local window instead of walking a larger comparison structure.

But there is an uncomfortable benchmark detail. My B+tree is sometimes slower than the sorted array. That almost certainly says something about my implementation, especially the 128 key leaf choice and its cache behavior, not that B+trees are secretly bad. A production implementation would be a much stronger baseline. I am leaving the result in because hiding it would make the comparison look cleaner than it is.

The memory result is harder to shrug off

Across the tested sizes, the learned structure uses roughly 688 times less index memory than my tree baseline. That is the part of the experiment that changed how I think about learned indexes. The model stores a compressed approximation of where keys live rather than explicitly storing a branching structure whose size grows with the dataset.

That smaller footprint also helps explain some of the lookup speed. Less index state means more of the working set can stay closer to the CPU. This is not only an algorithmic story about comparison counts. It is a memory hierarchy story.

Insert averages look great until you remember retraining exists

At 200,000 keys, the sorted array averaged 19.1 microseconds per insert. My B+tree took 2.78 microseconds. The learned index averaged 1.14 microseconds.

I would not ship based on that average. Most learned index inserts are cheap because they land in the delta buffer. Occasionally the buffer fills and the system pays for a merge plus a full retrain. That tail latency is exactly the kind of thing an average can make disappear. The benchmark proves the buffering strategy can keep average insert cost low. It does not prove the update path is pleasant in a real service.

The result I did not expect was lookup stability during writes

I expected lookups to slowly get worse as the delta buffer filled. They now have a second place to check when the base model misses. Instead, latency stayed near 117 nanoseconds through the insertion stream, while my tree baseline was around 250 nanoseconds in the same setup.

That is probably my favorite result in the project because it is less obvious than the static lookup win. The buffer absorbed writes without wrecking the base model's usefulness between retrains.

Where I think the idea actually fits

If the workload is read heavy and the key distribution has some stable structure, learned indexes are much more compelling to me after building one. Object storage metadata and ML data pipelines are obvious examples because they can involve huge numbers of small objects that are written once and read repeatedly. Cache sensitive in memory indexes are another plausible fit.

Once the workload becomes write heavy or highly concurrent, the elegance starts leaking. You have a base structure plus a buffer, retraining has to happen safely, and lookups cannot simply stop while the model is rebuilt. That concurrency problem is not a footnote. It is the gap between a nice benchmark and a thing I would trust in production.

What this benchmark does not prove

It never touches disk, so it says nothing direct about page cache behavior, storage latency, or crash recovery. It also uses synthetic key distributions. Those are useful for controlled comparisons, but real filesystem traces are burstier and stranger than a tidy generator.

The test is single threaded, with no locking or concurrent retraining. And the B+tree baseline is intentionally simplified. That last point matters a lot. The 4 times lookup advantage is a comparison against my B+tree implementation, not every B+tree anyone could write.

So I read the project as evidence that the index idea is worth taking seriously, not evidence that a learned index should replace a production filesystem tree tomorrow.

What I would build next

The next experiment I want is much less clean. Put the index behind real storage, use memory mapped or direct I/O, and see how much of the advantage survives when storage enters the timing path. I would also replace the delta buffer with a proper gapped array design closer to ALEX so inserts do not depend on periodic full retraining.

After that comes the part I avoided here: concurrency. Safe background retraining, simultaneous readers and writers, and actual filesystem traces are the things that would move this from “I understand the paper better now” toward “I might trust this design.”

Related work I found useful

  • TableFS and BetrFS put database style storage engines underneath filesystem metadata.
  • The Recursive Model Index by Kraska et al. is the paper that made the learned index framing click for me.
  • FITing Tree and the PGM index push the idea toward formal error bounds.
  • RadixSpline focuses on building the model quickly.
  • ALEX is the update friendly learned index that inspired the buffering strategy I used here.
  • SwiftKV applies learned indexes specifically to distributed filesystem metadata.
